## 1. 기술 스택 & 폴더 구조

- **모노레포**: pnpm workspaces + Turborepo
- **백엔드**: NestJS + Prisma ORM + PostgreSQL + Redis(ioredis, OTP 저장용)
- **프론트엔드**: Next.js (App Router, 클라이언트 컴포넌트 위주) + Tailwind CSS v4
- **인증**: JWT (세션 아님), 비밀번호 없음 — 휴대전화 OTP 전용
- **배치**: `@nestjs/schedule` Cron

```
scenefinder/
├─ apps/
│  ├─ web/        # Next.js 프론트엔드
│  └─ api/        # NestJS 백엔드
├─ packages/
│  └─ database/   # Prisma 스키마 + 마이그레이션 (공용 패키지)
└─ docs/          # PRD, DB스키마, 와이어프레임, 이용약관, 이 문서
```

DB 모델은 `packages/database/prisma/schema.prisma` 하나로 관리하고, API/프론트 모두 이 패키지를 통해 타입을 공유합니다.

## 2. 로컬 실행 방법

1. `docker-compose up -d` — PostgreSQL(5432), Redis(6379) 실행
2. `pnpm install`
3. `pnpm db:migrate` — 마이그레이션 적용 (`packages/database/.env`의 `DATABASE_URL` 사용)
4. `pnpm db:seed` — `shoot_categories` 등 기준 데이터 시딩
5. `pnpm dev` — web(:3000), api(:4000) 동시 실행 (Turborepo)

API 서버 환경변수(`apps/api/.env`): `DATABASE_URL`, `REDIS_URL`, `JWT_SECRET`, `JWT_EXPIRES_IN_SECONDS`, `PORT`, `FRONTEND_URL`, `TOSS_SECRET_KEY`(선택), `SETTLEMENT_FEE_RATE`, `PG_FEE_RATE`.

프론트 환경변수(`apps/web/.env`): `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_ASSET_BASE_URL`.

## 3. 인증 방식

PRD/DB문서는 "휴대전화 본인인증"이라고만 되어 있고 구체적인 인증 스킴은 정해두지 않았습니다. 실제로는:

- **비밀번호 없음.** 가입 시 이름/이메일/휴대전화만 받고, 로그인은 항상 OTP.
- OTP는 Redis에 6자리 코드로 저장(유효 180초), 검증 성공 시 JWT 발급.
- **`TOSS_SECRET_KEY`처럼 `.env`에 실제 SMS 발송 연동 키가 없으면, OTP 코드를 실제로 문자 발송하는 대신 서버 콘솔에 로그로 출력합니다** (`[OTP] 01012345678 -> 123456`). 개발 중에는 서버 로그에서 코드를 확인해 로그인 테스트를 합니다. 실제 SMS 연동 전까지는 이 방식이 유지됩니다.
- JWT는 `sub`(userId), `role`을 담고, `RolesGuard` + `@Roles('admin')` 데코레이터로 관리자 전용 라우트를 가드합니다.

## 4. 결제 연동 (Mock Fallback)

- 토스페이먼츠 연동 클라이언트(`TossPaymentsClient`)는 `TOSS_SECRET_KEY` 환경변수가 없으면 **자동으로 모의(mock) 결제 승인/취소 처리**로 전환됩니다. 실제 PG 서버를 호출하지 않고 항상 성공 응답을 만들어 반환합니다.
- 이유: 사업자 등록 및 PG 계약 전까지 결제 플로우 전체(예약금→잔금→정산)를 실제 돈 없이 끝까지 테스트하기 위함.
- 실제 서비스 오픈 전, `.env`에 `TOSS_SECRET_KEY`를 채우면 코드 변경 없이 실제 PG 연동으로 전환됩니다.
- 관리자 환불(`POST /admin/payments/:id/refund`)도 동일한 mock/실제 자동 전환 로직을 사용합니다.

## 5. 파일 업로드

PRD의 "결과물 전달"/"포트폴리오 등록"은 "클라우드 스토리지 사용 권장"이라고만 되어 있고 구체적인 구현은 없었습니다. 실제로는:

- `POST /api/uploads` — multer로 파일을 받아 **API 서버 로컬 디스크**(`apps/api/uploads/`, git에서 제외됨)에 저장하고 `{ url: '/uploads/파일명' }`을 반환.
- 이미지 mime 타입·용량 검증 포함.
- 포트폴리오 등록, 작가 촬영본 업로드(납품), 이 모두 이 엔드포인트를 공용으로 사용.
- **의도적으로 URL 기반 인터페이스**로 설계되어 있어서, 나중에 S3/R2 같은 실제 클라우드 스토리지로 바꿀 때 이 모듈(uploads.controller/service) 내부만 교체하면 되고, 나머지 코드(DB에는 URL 문자열만 저장)는 그대로 씁니다.

## 6. 확장성 설계 — shoot_categories 패턴

DB문서에 `shoot_categories` 테이블 자체는 있지만, 이게 실제로 어떻게 쓰이는지는 문서화되어 있지 않았습니다:

- `GET /api/shoot-categories` — 활성화된 촬영 분야 목록을 반환하는 **공개 엔드포인트**.
- 프론트엔드의 촬영 네비게이터 1단계, 포트폴리오 카테고리 탭, 작가 지원 폼의 전문분야 체크박스, 예약 문의 폼의 "촬영 종류" 선택 — **전부 하드코딩된 목록이 아니라 이 API를 호출**해서 동적으로 렌더링됩니다.
- 새로운 촬영 분야("시니어 투어" 같은)를 추가하려면 코드 배포 없이 `shoot_categories` 테이블에 row 하나만 추가(`sort_order`, `is_active` 지정)하면 모든 화면에 자동 반영됩니다.

## 7. 정산 로직 세부사항

PRD는 "수수료 15~20%"라고 범위로만 정해뒀는데, 실제 구현은 확정값 + env 설정으로 되어 있습니다:

- 플랫폼 수수료: `SETTLEMENT_FEE_RATE` (기본 15%)
- PG 수수료: `PG_FEE_RATE` (기본 3.3%, 작가 정산금에서 차감)
- 신규 작가(`is_new_photographer=true`) 첫 3건은 촬영완료 확인 후 **7일 유보**, 이후 표준 **3영업일 유보**
- `completed_bookings_count`는 고객이 납품을 확인(`POST /deliveries/:id/confirm`)하는 시점 + 자동확인 배치(미확인 +7일) 양쪽 경로 모두에서 증가합니다.

## 8. 취소 로직의 KST 타임존 처리

취소 규정("당일 취소" 여부 판단)은 서버가 어느 타임존에서 돌든 **한국 시간(Asia/Seoul) 기준으로 "같은 날"을 판단**해야 합니다. 단순히 `Date.toDateString()`으로 비교하면 서버 로케일에 따라 오탐이 발생할 수 있어서(예: UTC 20시 = 한국시간 다음날 새벽), `Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Seoul' })`로 날짜 문자열을 뽑아 비교하는 방식을 씁니다. (`apps/api/src/cancellations/cancellations.service.ts`)

## 11. 테스트용 계정

- 관리자 테스트 계정: 휴대전화 `01099998888` (role=admin). 비밀번호 없음 — 로그인 시 OTP 코드가 API 서버 콘솔 로그에 출력됩니다.
- 그 외 고객/작가 테스트 계정은 세션마다 만들고 검증 후 정리했기 때문에 남아있지 않습니다. 새로 회원가입해서 테스트하면 됩니다.

## 12. PRD 대비 현재 미구현 항목 (갭 목록)

PRD·DB문서에는 명시되어 있지만, 아직 코드로 구현되지 않은 것들입니다.

| 항목 | PRD 근거 | 현재 상태 |
|---|---|---|
| 일정 변경 요청/응답 (`POST /bookings/:id/reschedule-request`, `reschedule-response`) | DB문서 3-4 | **미구현.** 소통방 UI에 "일정 변경 요청" 버튼은 와이어프레임에만 있고 실제 동작 없음 |
| 작가 가능 일정 관리 (`PATCH /photographers/:id/schedule`) | DB문서 3-2, PRD 3-3 | **미구현.** DB에 일정/가용성 테이블 자체가 없음. 이중예약 방지는 슬롯 홀드(1시간)로만 처리 |
| 고객센터 일반/긴급 문의 (`POST /support/tickets`, `POST /support/emergency`) | DB문서 3-10 | **미구현.** 분쟁 신고(`/bookings/:id/disputes`)는 만들었지만, 그와 별개인 일반 1:1 문의·긴급 연락 채널은 없음 |
| 관리자 — 분쟁 처리 프론트엔드 | PRD 3-13 | **백엔드만 있음.** `fact-check-request`/`resolve`는 API로만 호출 가능, 관리자 화면 UI 없음 |
| 관리자 — 쿠폰 발행, 배너/카테고리 관리, CS 답변, 통계 다운로드 | PRD 3-13 | **미구현** (MVP 우선순위 낮음으로 보류) |
| 외국인 고객 지원 전체(다국어, 해외결제 등) | PRD 3-14 | **미구현** (PRD 자체가 MVP 제외로 명시) |
| 전자 계약서 생성/서명 (계약 항목 전체를 문서화한 정식 계약서) | PRD 3-7 | **미구현.** "중요 내용 확정" 버튼으로 소통방에 기록만 하고, 별도 계약서 PDF/전자서명은 없음 |
