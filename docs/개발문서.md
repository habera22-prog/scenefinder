## 1. 기술 스택 & 폴더 구조

- **모노레포**: pnpm workspaces + Turborepo
- **백엔드**: NestJS + Prisma ORM + PostgreSQL + Redis(ioredis, OTP 저장용)
- **프론트엔드**: Next.js (App Router, 클라이언트 컴포넌트 위주) + Tailwind CSS v4
- **인증**: JWT (세션 아님), 비밀번호 없음 — 휴대전화 OTP 전용
- **배치**: `@nestjs/schedule` Cron

```
scenefinder/
├─ apps/
│  ├─ web/        # Next.js 프론트엔드
│  └─ api/        # NestJS 백엔드
├─ packages/
│  └─ database/   # Prisma 스키마 + 마이그레이션 (공용 패키지)
└─ docs/          # PRD, DB스키마, 와이어프레임, 이용약관, 이 문서
```

DB 모델은 `packages/database/prisma/schema.prisma` 하나로 관리하고, API/프론트 모두 이 패키지를 통해 타입을 공유합니다.

## 2. 로컬 실행 방법

1. `docker-compose up -d` — PostgreSQL(5432), Redis(6379) 실행
2. `pnpm install`
3. `pnpm db:migrate` — 마이그레이션 적용 (`packages/database/.env`의 `DATABASE_URL` 사용)
4. `pnpm db:seed` — `shoot_categories` 등 기준 데이터 시딩
5. `pnpm dev` — web(:3000), api(:4000) 동시 실행 (Turborepo)

API 서버 환경변수(`apps/api/.env`): `DATABASE_URL`, `REDIS_URL`, `JWT_SECRET`, `JWT_EXPIRES_IN_SECONDS`, `PORT`, `FRONTEND_URL`, `KAKAO_REST_API_KEY`, `KAKAO_CLIENT_SECRET`, `KAKAO_REDIRECT_URI`, `TOSS_SECRET_KEY`(선택), `SETTLEMENT_FEE_RATE`, `PG_FEE_RATE`. 기본 예시는 `apps/api/.env.example` 참고.

프론트 환경변수(`apps/web/.env`): `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_ASSET_BASE_URL`.

## 3. 인증 방식

PRD/DB문서는 "휴대전화 본인인증"이라고만 되어 있고 구체적인 인증 스킴은 정해두지 않았습니다. 실제로는:

- **비밀번호 없음.** 일반 가입 시 이름/이메일/휴대전화만 받고, 전화번호 OTP로 인증합니다. 카카오 로그인도 지원하며, 첫 카카오 가입 시 기존 가입 정보(역할·이름·이메일·휴대전화)를 받고 전화번호 OTP를 확인합니다.
- OTP는 Redis에 6자리 코드로 저장(유효 180초), 검증 성공 시 JWT 발급.
- **`TOSS_SECRET_KEY`처럼 `.env`에 실제 SMS 발송 연동 키가 없으면, OTP 코드를 실제로 문자 발송하는 대신 서버 콘솔에 로그로 출력합니다** (`[OTP] 01012345678 -> 123456`). 개발 중에는 서버 로그에서 코드를 확인해 로그인 테스트를 합니다. 실제 SMS 연동 전까지는 이 방식이 유지됩니다.
- JWT는 `sub`(userId), `role`을 담고, `RolesGuard` + `@Roles('admin')` 데코레이터로 관리자 전용 라우트를 가드합니다.
- 카카오 로그인은 서버가 인가 코드 교환과 사용자 정보 조회를 처리하고, 자체 JWT를 발급합니다. `state`는 Redis에서 10분간 보관해 콜백을 검증하고, 서비스 JWT 대신 1회용 티켓만 프론트엔드로 전달합니다. 카카오 사용자 ID는 `social_accounts` 테이블에서 내부 회원과 연결합니다.
- 기존 계정과 이메일 또는 전화번호가 겹치면 자동 연결하지 않습니다. 해당 기존 계정에 전화번호 OTP로 로그인한 뒤 카카오 계정을 연결합니다. 카카오에서 이메일을 제공하지 않는 경우에는 가입 화면에서 직접 입력해야 합니다.
- 카카오 개발자 콘솔에 `KAKAO_REDIRECT_URI`와 정확히 같은 리다이렉트 URI를 등록해야 합니다. `KAKAO_REST_API_KEY`와 `KAKAO_CLIENT_SECRET`은 API 서버에만 설정합니다.

## 4. 결제 연동 (Mock Fallback)

- 토스페이먼츠 연동 클라이언트(`TossPaymentsClient`)는 `TOSS_SECRET_KEY` 환경변수가 없으면 **자동으로 모의(mock) 결제 승인/취소 처리**로 전환됩니다. 실제 PG 서버를 호출하지 않고 항상 성공 응답을 만들어 반환합니다.
- 이유: 사업자 등록 및 PG 계약 전까지 결제 플로우 전체(예약금→잔금→정산)를 실제 돈 없이 끝까지 테스트하기 위함.
- 실제 서비스 오픈 전, `.env`에 `TOSS_SECRET_KEY`를 채우면 코드 변경 없이 실제 PG 연동으로 전환됩니다.
- 관리자 환불(`POST /admin/payments/:id/refund`)도 동일한 mock/실제 자동 전환 로직을 사용합니다.
- 예약금/잔금 결제 버튼 위에는 결제 전 필수 고지(판매자인 작가의 상호·대표자·사업자등록번호·활동지역, 플랫폼의 통신판매중개자 고지, 결제 금액 내역)가 항상 노출됩니다 (PRD 4-2 근거, `apps/web/src/components/bookings/PaymentDisclosure.tsx`). 플랫폼 쪽 사업자등록번호·통신판매신고번호는 아직 실제 사업자 등록 전이라 "준비중"으로 표시되어 있음 — 실제 등록 후 이 컴포넌트의 하드코딩된 문구를 교체해야 합니다.

## 5. 파일 업로드

PRD의 "결과물 전달"/"포트폴리오 등록"은 "클라우드 스토리지 사용 권장"이라고만 되어 있고 구체적인 구현은 없었습니다. 실제로는:

- `POST /api/uploads` — multer로 파일을 받아 **API 서버 로컬 디스크**(`apps/api/uploads/`, git에서 제외됨)에 저장하고 `{ url: '/uploads/파일명' }`을 반환.
- 이미지 mime 타입·용량 검증 포함.
- 포트폴리오 등록, 작가 촬영본 업로드(납품), 이 모두 이 엔드포인트를 공용으로 사용.
- **의도적으로 URL 기반 인터페이스**로 설계되어 있어서, 나중에 S3/R2 같은 실제 클라우드 스토리지로 바꿀 때 이 모듈(uploads.controller/service) 내부만 교체하면 되고, 나머지 코드(DB에는 URL 문자열만 저장)는 그대로 씁니다.

## 6. 확장성 설계 — shoot_categories 패턴

DB문서에 `shoot_categories` 테이블 자체는 있지만, 이게 실제로 어떻게 쓰이는지는 문서화되어 있지 않았습니다:

- `GET /api/shoot-categories` — 활성화된 촬영 분야 목록을 반환하는 **공개 엔드포인트**.
- 프론트엔드의 촬영 네비게이터 1단계, 포트폴리오 카테고리 탭, 작가 지원 폼의 전문분야 체크박스, 예약 문의 폼의 "촬영 종류" 선택 — **전부 하드코딩된 목록이 아니라 이 API를 호출**해서 동적으로 렌더링됩니다.
- 새로운 촬영 분야("시니어 투어" 같은)를 추가하려면 코드 배포 없이 `shoot_categories` 테이블에 row 하나만 추가(`sort_order`, `is_active` 지정)하면 모든 화면에 자동 반영됩니다.

## 7. 정산 로직 세부사항

PRD는 "수수료 15~20%"라고 범위로만 정해뒀는데, 실제 구현은 확정값 + env 설정으로 되어 있습니다:

- 플랫폼 수수료: `SETTLEMENT_FEE_RATE` (기본 15%)
- PG 수수료: `PG_FEE_RATE` (기본 3.3%, 작가 정산금에서 차감)
- 신규 작가(`is_new_photographer=true`) 첫 3건은 촬영완료 확인 후 **7일 유보**, 이후 표준 **3영업일 유보**
- `completed_bookings_count`는 고객이 납품을 확인(`POST /deliveries/:id/confirm`)하는 시점 + 자동확인 배치(미확인 +7일) 양쪽 경로 모두에서 증가합니다.

## 8. 취소 로직의 KST 타임존 처리

취소 규정("당일 취소" 여부 판단)은 서버가 어느 타임존에서 돌든 **한국 시간(Asia/Seoul) 기준으로 "같은 날"을 판단**해야 합니다. 단순히 `Date.toDateString()`으로 비교하면 서버 로케일에 따라 오탐이 발생할 수 있어서(예: UTC 20시 = 한국시간 다음날 새벽), `Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Seoul' })`로 날짜 문자열을 뽑아 비교하는 방식을 씁니다. (`apps/api/src/cancellations/cancellations.service.ts`)

## 12. PRD 대비 현재 미구현 항목 (갭 목록)

PRD·DB문서에는 명시되어 있지만, 아직 코드로 구현되지 않은 것들입니다.

| 항목 | PRD 근거 | 현재 상태 |
|---|---|---|
| 외국인 고객 지원 전체(다국어, 해외결제 등) | PRD 3-14 | **미구현** (PRD 자체가 MVP 제외로 명시) |
| 연락처 비공개(안심번호·중계 이메일) + 강화된 PII 차단 | DB스키마 문서 `messages.pii_flag` 설계 의도 | **2차 과제로 보류(2026-08-15).** 현재는 (1) `chat.service.ts getContact()`가 예약금 결제 후 실제 전화번호·이메일을 그대로 상호 공개함 — 안심번호(050)·예약별 중계 이메일 같은 비공개 중계 구조가 전혀 없고, 이용약관 초안 제12조도 "직접 공개" 모델로 쓰여 있음. (2) `pii-detector.ts`는 전화번호·이메일 정규식만 감지하고, 카톡/인스타 ID·URL·메신저 ID·숫자 한글표기·명함이미지·QR코드는 감지 못 함. ## 13. 알림 시스템

PRD 3-3에 "알림: 문의 접수 → 수락 → 결제 요청 → ... (초기 이메일/사이트 알림, 이후 카카오 알림톡 확장)"이라고 명시돼 있었는데, 실제로는 세션 초중반까지 **완전히 빠져 있었습니다** — 뭔가 바뀌어도 직접 해당 페이지에 들어가봐야만 알 수 있는 상태였고, 실사용 테스트 중 발견되어 뒤늦게 추가했습니다.

- `notifications` 테이블: `userId`, `type`, `title`, `message`, `link`, `isRead`, `createdAt`. 실제 이메일/SMS/카카오 알림톡 발송은 아직 없고 **사이트 내 알림(in-app)만** 구현되어 있습니다 — PRD가 말하는 "초기 이메일/사이트 알림"의 사이트 알림 부분만 커버.
- 알림이 생성되는 이벤트: 예약 문의 생성(작가에게), 견적 제시(고객에게), 예약금/잔금 결제완료(작가에게), 취소(상대방에게), 일정변경 요청/응답(상대방에게), 분쟁 접수(상대방 + 전체 관리자에게), 분쟁 해결(양측에게), 문의 답변 완료(작성자에게), 사진 납품(고객에게).
- API: `GET /notifications`(최근 50건), `GET /notifications/unread-count`, `POST /notifications/:id/read`, `POST /notifications/read-all`.

## 14. 전자 계약서

PRD 3-7에 명시된 정식 계약서 생성/서명 기능입니다. 기존에는 예약 소통방에서 "중요 내용 확정" 버튼으로 텍스트 기록만 남겼는데, 실제로는 양측이 언제 무엇에 합의했는지 증빙할 수 있는 문서가 없었습니다.

- `contracts` 테이블: `bookingId`, `content`(텍스트 스냅샷), `customerSignedAt`, `photographerSignedAt`, `createdAt` (버전관리 관련 필드는 21번 항목 참고 — `bookingId` 단독이 아니라 `(bookingId, version)` 복합 unique).
- `GET /bookings/:id/contract`는 get-or-create 방식입니다 — 최초 호출 시점의 예약 정보(일시/장소/인원/목적/금액/작가 사업자정보/상품정보)로 계약서 본문을 마크다운 텍스트로 생성해 저장하고, 이후에는 같은 활성 버전을 반환합니다. 계약서는 **생성 시점의 스냅샷**이며, 양측 서명이 끝난 뒤 예약 조건이 바뀌면 자동으로 새 버전이 생성되어 재서명을 요구합니다 — 21번 항목 참고.
- `inquiry`/`quoted` 단계에서는 아직 계약서를 만들 수 없습니다(400 에러) — 견적 수락으로 `held` 상태가 된 이후부터 생성 가능. 예약금 대기 단계부터는 양측의 조건이 확정된 것으로 간주.
- `POST /bookings/:id/contract/sign`은 호출자가 고객인지 작가인지 자동 판별해 본인 쪽 서명 타임스탬프만 기록합니다. 실제 전자서명(공동인증서/생체인증 등)이 아니라, 로그인된 본인 계정으로 "동의" 버튼을 누른 시각을 남기는 **간이 서명**입니다.
- 프론트: 예약 소통방(`/bookings/[id]`) 하단에 `held` 상태 이후부터 계약서 카드가 표시되며, 내용 펼치기·서명 버튼·양측 서명 여부를 보여줍니다.
- 계약서 내용에는 취소·환불 정책, 일정변경 절차, 지각·노쇼 대응, 초상권·저작권, 개인정보 처리를 표준 문구로 포함시켜, 개별 예약마다 반복 협상할 필요가 없도록 했습니다.

## 15. 쿠폰 시스템

PRD 3-13 "쿠폰 발행"에 대응하는 기능입니다.

- `coupons` 테이블: `code`(unique), `name`, `discountType`(`fixed`|`percent`), `discountValue`, `maxDiscountAmount`(percent 할인의 최대 할인액 상한, 선택), `minOrderAmount`(선택), `maxRedemptions`(선택, null=무제한), `redemptionCount`, `expiresAt`(선택), `isActive`.
- `coupon_redemptions` 테이블: 쿠폰이 예약에 적용된 기록. `bookingId`가 unique라서 **예약 1건당 쿠폰 1개만** 적용 가능합니다. 적용 시점의 `originalTotalAmount`/`originalDepositAmount`/`originalBalanceAmount`를 그대로 저장해두기 때문에, 취소하면 할인 전 금액으로 정확히 복원됩니다.
- 적용 시점은 예약이 `quoted`(작가 견적 확인, 고객 수락 전) 상태일 때만 가능하도록 제한했습니다 — 예약금/잔금 결제가 시작되기 전에만 금액을 바꿀 수 있게 해서, 이미 계산·표시된 결제 금액과 어긋나는 문제를 원천 차단했습니다(관리자 예약 수정 기능과 동일한 이유).
- 할인액 계산: `fixed`는 `discountValue`원 그대로(단, 총액을 넘지 않도록 캡), `percent`는 `총액 × discountValue%`를 계산한 뒤 `maxDiscountAmount`가 있으면 그 값으로 다시 캡. 예약금/잔금은 할인 전 비율을 그대로 유지해 재분배합니다(예: 할인 전 예약금이 총액의 30%였다면, 할인 후에도 새 총액의 30%).
- 쿠폰 코드는 대문자로 정규화해서 저장/조회하므로 고객이 소문자로 입력해도 그대로 인식됩니다.
- 관리자는 쿠폰을 발행(`POST /admin/coupons`)하고 비활성화(`POST /admin/coupons/:id/deactivate`)할 수만 있습니다 — **발행 후 조건(할인율/금액 등) 수정 API는 의도적으로 없음**: 이미 그 쿠폰을 쓴 고객과의 형평성 문제가 생기기 때문입니다. 조건을 바꾸고 싶으면 기존 쿠폰을 비활성화하고 새 코드로 다시 발행하는 방식을 권장합니다.
- 프론트: 예약 소통방의 "견적 제시됨" 단계에 쿠폰 코드 입력창이 표시되고, 적용되면 할인액과 "쿠폰 취소" 버튼이 보입니다. 관리자 쿠폰 관리 화면(`/admin/coupons`)에서 발행/목록/비활성화가 가능합니다.

## 16. 관리자 통계 다운로드

PRD 3-13 "통계 다운로드"에 대응하는 기능입니다. 범위는 **완료된 결제 내역(예약금/잔금) CSV 내보내기**로 한정했습니다 — 매출·정산 대사(회계/세무 확인)에 실질적으로 필요한 데이터가 결제 원장이기 때문입니다.

- `GET /admin/stats/export?from=YYYY-MM-DD&to=YYYY-MM-DD`: `status='completed'`인 결제만 대상으로, 결제ID/예약ID/고객명/작가상호/결제유형/금액/PG사/결제일시 컬럼의 CSV를 반환합니다. `from`/`to`는 둘 다 선택 — 비우면 전체 기간.
- 응답은 `Content-Type: text/csv`, `Content-Disposition: attachment`로 내려가며, 엑셀에서 한글이 깨지지 않도록 **UTF-8 BOM**을 맨 앞에 붙였습니다.
- 프론트(`apps/web/src/lib/api.ts`의 `downloadFile()`): 기존 `apiFetch`는 JSON 응답만 가정하므로, CSV처럼 파일을 내려받는 요청은 별도 함수로 분리했습니다 — `fetch`로 받은 응답을 Blob으로 변환한 뒤 `<a download>`를 코드로 클릭시켜 브라우저 다운로드를 트리거합니다. 관리자 대시보드(`/admin`)에 기간 선택 후 "CSV 다운로드" 버튼으로 노출됩니다.
- 프론트: 헤더의 알림 종 아이콘(`NotificationBell.tsx`) — 15초 간격 폴링으로 안읽은 개수 배지 표시, 클릭 시 목록 드롭다운 + 해당 페이지로 이동하며 자동 읽음처리.
- 이메일/카카오 알림톡 연동은 아직 없음 — 나중에 추가한다면 `NotificationsService.create()` 호출 지점에 발송 로직만 추가하면 되도록 이미 단일 진입점으로 모아뒀습니다.

## 17. 촬영 방식(capture mode) — 촬영 종류와 분리된 축

PRD·DB문서에는 "드론", "영상"이 `packages.options`(추가옵션) 안의 자유 항목 정도로만 암시되어 있었는데, 실제로는 촬영 종류(행사/가족 등)와는 별개로 검색·필터링이 되어야 할 축이라 `shoot_categories`와 같은 패턴의 독립 테이블로 뺐습니다.

- `capture_modes` 테이블: `code`(unique, 예 `photo`/`drone`/`video`/`photo_drone`/`all`), `label`, `isActive`, `sortOrder` — 6번 항목의 `shoot_categories`와 동일한 확장 패턴. 새 조합을 추가해도 코드 배포 불필요.
- `GET /capture-modes` — 공개 엔드포인트, 활성화된 목록 반환.
- 작가(`photographers.captureCapabilities`, 문자열 배열)는 지원 시 본인이 수행 가능한 촬영 방식을 전부 선택합니다 — `categories`와 동일하게 느슨한 문자열 매칭이라 `capture_modes`에 없는 값이 섞여도 DB 레벨에서 막지 않습니다(운영 정합성은 관리자 화면 목록에서만 보장).
- 상품(`packages.captureModeCode`)과 예약(`bookings.captureModeId`)에도 선택적으로 촬영 방식을 지정할 수 있습니다. 상품은 문자열 코드(느슨한 매칭), 예약은 실제 FK(`capture_modes.id`)로 참조 방식이 다릅니다 — 예약 쪽은 촬영 방식별 통계·정산 확장을 염두에 두고 FK로 설계했습니다.
- 검색(`GET /photographers`)과 네비게이터(`/navigator`)는 `captureMode` 쿼리 파라미터로 필터링하며, 작가의 `captureCapabilities`에 해당 코드가 포함되어 있는지로 매칭합니다.
- 관리자 CRUD: `GET/POST /admin/capture-modes`, `PATCH /admin/capture-modes/:id` (`/admin/capture-modes` 화면).

## 18. 사업자 미등록 프리랜서 작가 유형

PRD 3-12는 "비사업자 개인은 포트폴리오 등록·지원 신청만 가능"이라고 되어 있었고, 이전 버전 이 문서(2026-08-14 기준)에는 이를 아예 미구현으로 남겨두기로 한 결정이 적혀 있었습니다. 이후 정책이 바뀌어 **사업자등록 없는 개인도 정식으로 유료 촬영 작가로 활동**할 수 있도록 `PhotographerType`(`business`/`freelancer`) 유형을 추가했습니다 — 아래는 그 대체 설계입니다.

- `photographers.photographerType`: `business`(기본값) 또는 `freelancer`. `businessRegNo`/`businessName`/`representativeName`은 **BUSINESS만 필수**로 nullable 처리했습니다.
- 지원 시(`POST /photographers/apply`) `photographerType`을 명시해야 하며, `freelancer`면 사업자 관련 3개 필드를 보내지 않아도 됩니다(DTO는 `ValidateIf`로 조건부 필수 처리).
- **승인 안전장치**: `POST /photographers/business-verification`(사업자등록 형식 검증)은 `photographerType !== 'business'`면 400으로 거부합니다 — freelancer는 이 경로로 `verified`에 도달할 수 없고, 오직 관리자 승인(`POST /admin/photographers/:id/approve`)을 통해서만 인증됩니다. 즉 "사업자 인증 없이는 절대 verified로 못 가게" 하는 안전장치는 사업자 여부와 무관하게 관리자 심사가 최종 게이트라는 기존 구조를 그대로 활용했습니다.
- 계약서(`buildContractContent`)·결제 전 고지(`PaymentDisclosure.tsx`)·작가 카드·관리자 작가 목록 등 사업자 정보를 노출하던 모든 화면은 `photographerType`에 따라 "상호·대표자·사업자등록번호" 대신 "OO님 (SceneFinder 인증 프리랜서 작가 — 사업자 미등록)"으로 분기 표시합니다.
- **기업 전용 촬영 제한과 연동**: `shoot_categories.businessOnly=true`인 분야(기업/기관/브랜드 등)나 `bookings.taxInvoiceRequired=true`(세금계산서 필요) 예약은 `photographerType='business'`인 작가에게만 배정 가능하도록 예약 생성(`POST /bookings`)과 검색(`GET /photographers`) 양쪽에서 차단합니다 — freelancer가 세금계산서를 발행할 수 없기 때문입니다.

## 19. 분야별 시간당 최저가 하한선

DB문서·PRD 어디에도 명시되지 않은, 운영 중 발견된 문제에 대한 대응입니다: 플랫폼 수수료(정산 시 차감)를 피하려고 작가와 고객이 짜고 견적을 비정상적으로 낮게 신고한 뒤 나머지를 현금으로 주고받을 유인이 있습니다.

- `shoot_categories.minHourlyRate`(선택, 원 단위): 관리자가 분야별로 시간당 최저가를 지정할 수 있습니다. `null`이면 제한 없음.
- 상품 등록(`POST /photographers/:id/packages`)과 맞춤 견적 제시(`POST /bookings/:id/quote`) 양쪽에서 `금액 < 최저가 × (분/60)`이면 400으로 차단합니다.
- 상품이 없는 맞춤 견적은 `durationMin`(촬영 시간, 분)을 별도로 받아야 검증할 수 있어서, `CreateQuoteDto.durationMin`을 선택 필드로 추가했습니다 — 프론트는 예약에 연결된 상품이 없을 때만 이 입력창을 보여줍니다.
- 관리자 카테고리 관리 화면(`/admin/categories`)에서 분야별로 최저가를 입력/수정할 수 있습니다.

## 20. 기업/기관 맞춤촬영 및 제휴 문의

PRD 3-14 "외국인 고객"처럼 별도 접수 흐름이 필요한 카테고리로, 기업/기관의 대규모·맞춤 촬영 문의와 여행사·업체 등의 제휴 제안을 위한 **비회원도 제출 가능한 문의 폼**을 추가했습니다. 일반 예약(`Booking`) 플로우와 의도적으로 분리했습니다 — 이런 문의는 즉시 매칭되는 것이 아니라 관리자가 검토 후 작가/촬영팀을 별도로 구성하는 영업 프로세스이기 때문입니다.

- `corporate_inquiries` 테이블: 회사명/담당자/연락처/희망일시/장소/목적/촬영방식/예상시간/예상인원/결과물 용도/예산대/세금계산서 필요 여부/메모, `status`(`received`/`reviewing`/`matched`/`closed`), `adminMemo`.
- `partnership_inquiries` 테이블: 회사명/담당자/연락처/업체 유형(여행사/행사대행사/호텔/드론업체 등)/제휴 형태/제안 내용, 동일한 `status`/`adminMemo`.
- `POST /inquiries/corporate`, `POST /inquiries/partnership` — **인증 없이(비회원) 호출 가능**한 유일한 쓰기 엔드포인트들입니다. 프론트 `/business-inquiry`, `/partnership` 페이지에서 제출.
- 관리자는 `GET/PATCH /admin/inquiries/corporate`, `GET/PATCH /admin/inquiries/partnership`(`/admin/inquiries` 화면)로 목록을 조회하고 상태·메모만 갱신합니다 — 문의 내용 자체를 수정하는 API는 없습니다(제출자 원본 보존).
- `bookings.dealType`(`standard`/`custom_contract`/`partnership`, 기본 `standard`) 필드를 미리 추가해뒀지만, 이번 구현에서는 실제로 `custom_contract`/`partnership`을 만드는 코드 경로는 없습니다 — 문의가 실제 예약으로 이어질 때 이 필드를 어떻게 채울지는 향후 과제로 자리만 잡아둔 상태입니다.

## 21. 전자 계약서 버전관리(재서명)

14번 항목의 "계약서는 생성 시점의 스냅샷이며 예약 내용이 바뀌어도 자동 갱신되지 않는다"는 한계를 해소한 기능입니다. 특히 일정 변경 승인처럼 예약 조건이 실제로 바뀌는데 이미 양측이 서명한 계약서가 그대로 남아있는 것은 법적 증빙으로 문제가 될 수 있습니다.

- `contracts.version`(정수, 예약당 1부터 증가), `contracts.status`(`active`|`superseded`), `contracts.changeReason`, `contracts.previousVersionId`(자기참조 FK) 추가. `bookingId` 단독 unique 제약은 `(bookingId, version)` 복합 unique로 대체되어 예약 1건이 여러 버전의 계약서를 가질 수 있습니다.
- 새 버전은 **아무 때나 만들어지지 않습니다** — 현재 활성 계약서가 **양측 모두 서명 완료**된 상태에서만 트리거됩니다. 아직 미서명 상태라면 최초 생성 시점 정보로 충분하다고 보고 버전을 올리지 않습니다.
- 현재 트리거 지점은 하나뿐입니다: 일정 변경 요청이 승인되어 예약의 `shootDatetime`/`location`이 실제로 바뀔 때(`POST /bookings/:id/reschedule-response`) `ContractsService.createNewVersion(bookingId, '일정 변경으로 인한 재계약')`을 호출합니다. 금액 변경(쿠폰 적용 등)은 아직 트리거하지 않습니다 — 향후 트리거 지점을 늘릴 때는 이 메서드를 재사용하면 됩니다.
- 새 버전 생성 시 기존 버전은 `status='superseded'`로 바뀌고, 새 버전이 `status='active'`가 되며 양측 서명 타임스탬프는 초기화됩니다(재서명 필요). 양측 모두에게 "계약서가 갱신되었어요" 알림이 발송됩니다.
- `GET /bookings/:id/contract`(get-or-create), `POST /bookings/:id/contract/sign`은 항상 **활성 버전** 기준으로 동작하도록 수정되었습니다. `GET /bookings/:id/contract/history`로 전체 버전 이력(버전 번호/상태/변경 사유/생성 시각)을 조회할 수 있습니다.
- 프론트(`ContractView.tsx`): 계약서 카드에 버전 번호를 표시하고, `version > 1`이면 갱신 사유 안내 배너를 보여줍니다. "이전 버전 보기"를 누르면 이력을 지연 로딩합니다.
